# 智慧医疗 7 级专科体系建设方案

**基于专病指南知识图谱的独立专科诊疗体系与全诊疗周期医嘱推荐**

> 定位：本文是 `cdss-knowledge-engine` 项目面向《智慧医疗分级评价方法及标准（2025 版）》7 级专科条款的总体建设方案，覆盖知识生产、决策服务、业务集成、组织治理、评审取证五个层面，并给出与现有代码模块的落地对照。

---

## 0. 一页纸结论

1. **条款定位**：所引条款出自 2025 版标准（修订替代 2018 版电子病历分级评价）的"专科"新增要求——**6 级须建成 1 个专科的独立诊疗体系，7 级须不少于 3 个专科**（"重点优先"），共 35 项专科指标。这句话同时是 6 级（单专科版）与 7 级（3+专科版）的核心条文。
2. **一句话拆解**：评审要的不是"一个 CDSS"，而是四件事——**独立专科诊疗体系**（专科维度的组织与知识独立）、**全诊疗周期完整医嘱管理体系**（门诊→住院→出院→随访的医嘱全覆盖 + 闭环）、**符合专科指南的独立处理过程与专科知识库**（知识资产有出处、可溯源、有人管）、**基于专病指南/专家共识的医嘱推荐**（推荐要落到开单动作，可演示、可统计）。
3. **现有引擎的位置**：本引擎已经是"知识生产层"的雏形——指南 PDF→模板抽取→知识图谱→规则→审核→知识包，且西医治疗域（treatment_plan/优先级/禁忌/监测）与中医域（辨证→治法→方药）均已成型。**缺的是三块：医嘱本体与医嘱套餐、诊疗路径（全周期）建模、面向 HIS/CPOE 的推荐服务与闭环核查。**
4. **架构主张**：把"知识生产线"与"知识消费端"解耦。引擎负责把指南变成**可版本化的专科知识包**（图谱+规则+路径+医嘱套餐+量表），通过推荐/审核 API 供 HIS 医师工作站调用；医嘱闭环、病历模板等由 EMR/HIS 承接，CDSS 在开立、审核、执行三个环节嵌入核查点。
5. **三专科组合建议**：**心血管内科**（锚定，已有 STEMI/暴发性心肌炎/肥厚型心肌病资产）+ **血液/肿瘤科**（已有淋巴瘤分期分型抽取资产）+ **中医科**（TCM 域已成型，直接命中新版 32 项中医中药条款，一份投入双重得分）。
6. **必要非充分**：专科条款只占 7 级 752 项指标的一部分。冲 7 级还需同步满足 22 个闭环场景（多数为 6 级门槛）、17 项 AI 要求、区域信息利用、医疗安全质量管控等，本文第 1.4 节给出全景对照，路线图按"6 级地基 + 7 级增量"编排。

## 1. 评审要求解读

### 1.1 标准沿革与定位

2025 年国家卫健委发布《关于征求智慧医疗分级评价方法及标准（2025 版）意见的函》，在 2018 版《电子病历系统应用水平分级评价标准（试行）》基础上全面修订：名称由"电子病历系统应用水平分级评价"改为"**智慧医疗分级评价**"；级别由 0–8 级调整为 **1–8 级**；工作角色由 10 个调整为 **12 个**（新增"医疗质量管理""电子病历安全"）；业务项目调整为 **38 项**（含新项目"**知识获取及管理**"——恰是本引擎的直接定位）；评价指标由 779 项调整为 **752 项**（新增 282 项，主要集中在 5、6 级与专科、AI、中医方向）。

各级主线：6 级 = 全流程数据闭环管理 + 高级医疗决策支持 + 区域信息引用 + **专科病历支持**；7 级 = 医疗安全质量管控 + **构建专科诊疗体系** + 区域医疗信息利用；8 级 = 大健康信息整合。

> 注意：截至本方案撰写，2025 版仍为征求意见稿形态，正式印发后条款编号与个别阈值可能微调，落地时以正式文本为准做一轮条款对照更新。2018 版在 6 级"高级医疗决策支持"中同样有知识库与专科处理相关要求，两版在专科方向上是连续加码的关系。

### 1.2 专科条款精读

标准原文（专科条款示例，7 级）：

> 不少于 3 个专科（重点优先）纳入独立专科诊疗体系，可覆盖专科全诊疗周期的完整医嘱管理体系，有针对专科疾病符合专科指南要求的独立处理过程及专科知识库，支持基于专病指南或专家共识的专科诊疗内容医嘱推荐。

配套专科条款还包括：

- 可依据专科、诊断等**自动推荐智能评估模板**，有针对评估内容的智能检查与提示，**高风险护理评估结果能主动通知医生**（如有中医病房，依据内容还应包括四诊及病因病位等辨证内容）；
- 建立针对不同专科、病种的**诊疗模型**，结合全周期数据，形成**风险预测模型**。

把主条款拆成四个能力域，每个能力域对应可建设、可演示、可取证的系统构件：

| # | 条款短语 | 能力域 | 系统构件（谁来做） |
|---|---------|--------|------------------|
| ① | 独立专科诊疗体系 | 专科是独立的管理单元：有自己的知识库、术语集、路径、模板、权限 | 知识引擎：专科知识包 + 专科 Profile；HIS：专科字典与权限 |
| ② | 覆盖专科全诊疗周期的完整医嘱管理体系 | 门诊→入院→评估→治疗→疗效评价→出院→随访的医嘱类型全覆盖（药/检/查/治/护/宣教/随访）+ 医嘱闭环 | 引擎：诊疗路径模型 + 医嘱套餐；HIS：医嘱闭环状态机 |
| ③ | 符合专科指南要求的独立处理过程及专科知识库 | 知识有出处：每条处理过程/规则/医嘱套餐可溯源到指南条目（版本、章节、页码），有审核与更新机制 | 引擎：图谱溯源（已有 Source）+ 审核工作流（已有）+ 版本化发布 |
| ④ | 基于专病指南或专家共识的专科诊疗内容医嘱推荐 | 推荐是"动作"：在开单场景给出可一键引用的医嘱套餐，附证据链；可统计推荐与采纳 | 引擎：推荐服务 API；HIS：CPOE 嵌入推荐卡片 |

**取证视角**：评审专家在现场核查时，对这四条分别会看——①专科清单与各自知识库界面；②按一个真实专病患者走全流程，医嘱从入院开到随访、闭环状态可查；③任点一条规则/医嘱能翻出指南原文（页码级）与审核记录；④开单界面实时演示推荐 + 推荐量/采纳率的运行统计。方案第 8 节据此设计演示脚本。

### 1.3 配套联动条款（同一张 7 级试卷的邻题）

- **闭环管理**：22 个闭环场景被明确列举（医嘱、检查记录、检验过程、药品使用、会诊、不良事件、治疗过程等），医嘱执行闭环为 5 级，其余多为 6 级——**是 7 级的地基，且全部与医嘱体系直接相关**。
- **人工智能（17 项，基本 7、8 级）**：用药方案推荐、检查方案推荐、智能内涵质控、知识图谱、AI 模型、病历书写、评估模板推荐；其中"知识图谱内容可引入与管理，构建可持续更新的知识库及人工智能模型"与引擎的抽取→审核→发布流水线直接对应。
- **中医中药（32 项）**：十八反/十九畏/禁忌检查、中医临床路径、中医病历结构化（疾病诊断/证候诊断/四诊）、中药处方规范、调护执行记录——**TCM 域选一个专科可同时吃两份条款分**。
- **易用性（35 项）**：同屏显示、颜色标记、实时提示——推荐卡片必须"同屏、免切换、一键引用"，这是交互验收的硬约束。
- **医疗准入与职权管理**：药品/手术/治疗/操作/输血的独立授权与分级授权闭环——专科医嘱推荐必须接医生权限做过滤（无权限的套餐条目要置灰并提示申请授权）。

### 1.4 7 级全景与专科体系的边界

7 级 = 专科诊疗体系（本文主线）+ 医疗安全质量管控（预警/通报体系）+ 区域医疗信息利用（院内外双向交换）。专科体系建设是**必要非充分**条件；路线图（第 9 节）把闭环、质量管控等 6 级地基项排在专科扩展之前，避免"专科做得很炫、地基指标失分"的常见陷阱。

## 2. 总体架构：五层体系

```
┌─────────────────────────────────────────────────────────────────┐
│ ⑤ 治理与运营层   知识管理制度 · 专家审核委员会 · 版本/更新机制      │
│                 推荐采纳率等运营指标 · 评审取证材料                │
├─────────────────────────────────────────────────────────────────┤
│ ④ 业务集成层     医师工作站(CPOE)同屏推荐卡 · 医嘱闭环(HIS)        │
│                 专科病历模板 · 评估模板/高风险通知 · 护理联动       │
│                 CDR/数据中台 · HIS/LIS/PACS 集成                  │
├─────────────────────────────────────────────────────────────────┤
│ ③ 决策服务层     医嘱推荐引擎(诊断→分期→方案→医嘱套餐实例化)        │
│                 开单实时核查(禁忌/重复/剂量/权限) · 评估与风险模型  │
├─────────────────────────────────────────────────────────────────┤
│ ② 知识资产层     专科知识包: 知识图谱 · 规则库 · 诊疗路径          │
│                 医嘱套餐库 · 评估量表库 · 术语映射 · 版本与溯源     │
├─────────────────────────────────────────────────────────────────┤
│ ① 知识生产层     指南遴选→PDF解析→模板抽取→概念映射→候选规则       │
│                 →人工审核(门禁)→知识包发布   ← 本引擎现有主体      │
└─────────────────────────────────────────────────────────────────┘
```

分层原则：

- **①②层归知识引擎**（本项目）：把指南变成"可发布的知识资产"，一切结论可溯源。这是医院自建可控、评审必查、且一旦建成可向所有专科复制的能力。
- **③层是引擎的 API 化**：推理引擎从"表单演示"升级为"服务消费"—— HIS 事件驱动调用，输出结构化推荐。
- **④层归 EMR/HIS 厂商协同**：推荐卡片嵌入、医嘱闭环、专科模板；引擎提供标准契约（接口 + 术语），不侵入 HIS 内核。
- **⑤层归医院管理**：制度、委员会、指标——评审不仅看系统还看机制，制度文件与审核记录是取证材料的一部分。

**结论：知识生产层（①层）骨架完整，②层缺四类资产——医嘱本体、诊疗路径、评估量表、风险模型——以及贯穿的版本化专科知识包。**

### 3.2 医嘱本体与医嘱套餐（Order Set）

推荐要落到"开单动作"，图谱必须有医嘱层。在现有实体之外新增：

- **order_item（医嘱条目）**：医院真实可开的原子医嘱，属性含 `order_class`（药品/检验/检查/治疗/手术/护理/宣教/随访）、标准编码（药品用医保码/本位码，检验用 LOINC，诊断用 ICD-10）、默认频次/用法/剂量、与院内医嘱字典的映射码。
- **order_set（医嘱套餐）**：一组 order_item 的有序集合，是**推荐的基本单位**。属性：适用条件摘要、包含条目（含必选/可选/按需勾选）、禁忌过滤规则、指南出处。
- 关系：`disease/stage → indicated_by → treatment_plan → materialized_as → order_set → contains → order_item`；`order_item ←maps_to→ 院内医嘱字典项`。

设计要点：

1. **套餐条目逐条挂 Source 溯源**。评审演示的高光动作是"点开推荐里的一条医嘱→翻到指南原文页"——这要求 order_item 上的 evidence 关系落到 chunk/page 级（复用现有 RuleSource 结构）。
2. **参数化**。剂量按体重/肌酐清除率/年龄折算，检验阈值按院标准（复用 `data/standards/` 多院配置机制）——"推荐"给出的必须是本院可执行的数值，而不是指南原文的"XX mg/kg"。
3. **权限与授权过滤**。order_item 关联手术/操作分级授权（条款：医疗准入与职权管理），推荐时按医生权限过滤或置灰提示。
4. 与现有 `treatment_items` 的关系：RuleConclusion.treatment_items 是规则结论内嵌的治疗条目（图谱实体级），order_set 是其"可下单实例化"的投影——治疗规则命中后，由推荐服务把 treatment_plan 物化为 order_set。两层分离，图谱保持指南视角，套餐保持医院执行视角。

### 3.3 诊疗路径建模（全诊疗周期）

条款②"覆盖专科全诊疗周期的完整医嘱管理体系"要求把单点规则串成周期路径。新增：

- **care_pathway（专科诊疗路径）**：`phases = [门诊/急诊, 入院评估, 分期分型, 治疗(一线/二线/姑息等分支), 疗效评价, 出院准备, 随访]`。
- 每个 phase 绑定：触发条件（入院完成/诊断确立/治疗满 N 天）、入口评估（量表）、**该阶段的默认医嘱套餐集**、出口条件（转段规则）、变异记录点。
- 与临床路径系统（HIS 侧）的关系：知识引擎管"应该怎样"（指南视角的路径知识），HIS 临床路径模块管"实际入径/执行/变异"（执行视角），两者通过 pathway_id 对齐。评审演示时"入径患者自动带出阶段套餐"即是这两个系统的合演。

以 STEMI 为例的全周期骨架（示意）：

```
急诊胸痛 → [评估套餐: 心电图/肌钙蛋白+D2D计时] → 确诊STEMI(诊断规则)
  → [再灌注套餐: 导管室激活/抗栓负荷剂量(按体重/肾功能)] → PCI术后
  → [监护套餐+监测要求] → [二级预防套餐: 双抗/他汀/β受体阻滞剂+宣教]
  → 出院评估 → [随访套餐: 1/3/6月复查计划]
```

### 3.4 评估量表与风险模型

对应配套条款"自动推荐智能评估模板、评估内容智能检查与提示、高风险主动通知医生"与"风险预测模型"：

- **assessment_scale（评估量表）**：条目、计分规则、分级切点（如 GRACE 评分→死亡风险层、出血评分 HAS-BLED→出血风险层）。量表落库为可执行计分规则（现有规则引擎可承载），并作为 `staging` 推理阶段的输入。
- **风险通知规则**：评估结果达高危阈值 → 推送事件给医师工作站/护理站（走集成层消息通道，引擎只发结构化事件，通知界面由 HIS/集成平台渲染）。
- **风险预测模型**：结合 CDR 全周期数据训练（再入院、死亡、出血等），以模型服务形态挂在路径 phase 上作为辅助分层依据。2025 版 AI 条款明确要求"知识图谱可引入与管理、构建可持续更新的知识库及人工智能模型"——**图谱与模型双资产**正是引擎定位。

### 3.5 版本化专科知识包

把现有 guide_packages 升级为 specialty knowledge package：

- 包内含：图谱切片 + 规则集 + 路径 + 医嘱套餐 + 量表 + 术语映射，**整体版本号**（semver），生效/失效日期，与指南版本对齐（如《中国胸痛诊疗指南 2024 版》→ 知识包 v2.x）。
- 发布流：抽取 → 审核门禁（已有）→ 预检（package_checks 扩展：医嘱条目必须有院内映射、套餐必须可溯源）→ 灰度（单病区启用）→ 全院发布。支持 diff（新旧版规则/套餐差异清单）与一键回滚。
- 指南更新触发机制：知识专员盯更（学会/期刊发布新指南）→ 建新版本包 → 走完整审核。评审问"指南更新了怎么办"时，展示版本链与更新 SOP。

## 4. 医嘱推荐引擎（③层核心服务）

### 4.1 触发时机与推荐流程

事件驱动（HIS/CDR 推送给引擎），四类触发点：

| 触发事件 | 推荐内容 |
|---------|---------|
| 患者入径/入院完成 | 阶段默认套餐（评估类医嘱优先） |
| 诊断确立/更新（含 AI 病历内涵识别辅助） | 该诊断+分期的治疗套餐 |
| 评估量表完成 | 风险分层驱动的检查/治疗调整建议 + 高危通知 |
| 医生打开开单界面（被动查询） | 当前路径阶段的套餐 + 个性化提示 |

推荐流水线（复用现有推理引擎，扩展两个阶段）：

```
患者全周期上下文(CDR)
  → staging 阶段: 评估计分/分期分型规则 → 产生 fact（如 GRACE=高危）
  → diagnosis 阶段: 现有诊断规则（已具备）
  → treatment 阶段: 现有治疗规则 → treatment_plan（已具备）
  → materialize 步骤(新增): treatment_plan → order_set 实例化
      · 按 order_item 本院映射生成可下单条目
      · 剂量/阈值参数化（体重、肾功能、年龄、本院 standards）
      · 安全过滤（禁忌、过敏、相互作用、重复检验、医生权限）
  → 推荐卡片输出（内容 + 理由 + 证据链 + 一键引用动作）
```

### 4.2 推荐输出契约（API 形态）

`POST /api/recommendations`（新增路由），请求：`{patient_ref, encounter phase, trigger_event, context}`；响应要点：

```jsonc
{ "recommendations": [{
    "id": "REC-...", "type": "order_set",
    "order_set_id": "OS-STEMI-REPERFUSION",
    "title": "STEMI 再灌注医嘱套餐（首选）",
    "priority": "preferred",              // 复用现有优先级语义
    "reason": "确诊 STEMI（证据：持续胸痛+ST抬高+肌钙蛋白升高）",
    "evidence": [{ "rule_id": "...", "guideline": "中国胸痛诊疗指南2024",
                   "section": "再灌注治疗", "page": 12, "quote": "…" }],
    "items": [ /* 已参数化的本院可执行医嘱条目，含 required/optional */ ],
    "action": { "kind": "insert_orders", "payload": "HIS 医嘱草稿格式" },
    "expires_at": "…", "status": "pending" } ],
  "alerts": [ /* 高危评估通知 */ ] }
```

配套两个回写接口：**采纳/拒绝反馈**（`POST /api/recommendations/{id}/feedback`，供采纳率统计——评审必看的运行指标）与**推荐日志查询**（运行数据取证）。

### 4.3 安全核查（嵌入闭环的 CDSS 检查点）

开单环节实时核查（引擎同步接口，<300ms 目标）：禁忌过滤（contraindication 节点 + 十八反/十九畏 TCM 规则）、剂量上限/肾功能折算核查、重复检验/检查识别（同路径阶段已开同类医嘱）、相互作用、权限校验。核查结果分级：阻断（红）/警示（黄）/提示（蓝），对应易用性条款的颜色标记要求。

### 4.4 与现有推理分期的衔接

现有 western stages 为 `diagnosis → treatment`（tcm 为辨证→治法→方药→禁忌四段）。扩展为 `assessment → staging → diagnosis → treatment → materialize`，其中 assessment/staging 产生 facts 供后续阶段消费（机制已有：`produces_facts` + `fact` 条件类型），materialize 不产生临床结论、只做工程物化——保持规则语义与执行语义分离。

## 5. 业务系统集成（CDSS 之外的部分）

### 5.1 医师工作站同屏集成

推荐卡片以侧栏/浮层嵌入 HIS 开单界面（或集成平台提供的标准嵌入件），满足"同屏直接查阅、免切换、一键引用"的易用性硬约束。引用动作 = 把 order_set 实例化的条目写入医嘱草稿，医生确认后走正常开立流程——**推荐不替代医生签字**，这是医疗安全与评审的共同底线。

### 5.2 医嘱闭环与 CDSS 核查点

医嘱闭环（开立→审核→摆药/配液→执行→计费→结果回报→评价）的执行主体在 HIS，但 22 个闭环场景中 CDSS 承担三类角色：开立前（套餐推荐）、开立时（安全核查）、闭环后（结果回报驱动的再评估——如肌钙蛋白回报触发诊断规则、疗效评价阶段自动比对目标值）。集成方式建议：集成平台事件总线（推荐 HL7 FHIR / 平台消息），引擎订阅 `order-placed`、`result-ready`、`diagnosis-updated` 等事件。

### 5.3 术语标准与映射

专科体系的术语底座：诊断 ICD-10（已有 `seed_icd10_reference`，建议预留 ICD-11 映射）、检验 LOINC、药品医保编码/本位码、手术操作 ICD-9-CM-3、中医病证编码（GB/T 15657）。院内本地码→标准码映射已有 `src/terminology/mapper.py` 机制，扩展为三向：本地码 ↔ 标准码 ↔ 图谱实体 code，并纳入知识包版本管理（换码表=换版本）。

### 5.4 CDR 与全周期数据

推荐质量取决于患者上下文完整度：诊断、检验（含历史趋势——ULN/动态趋势评估器已具备）、检查报告、用药、过敏、手术史、评估记录、随访记录。建议以 CDR/数据中台为唯一事实源向引擎供数；全周期数据同时反哺风险模型训练（条款："结合全周期数据，形成风险预测模型"）。注意脱敏与权限：引擎按需最小化取数，操作留审计（已有 audit 机制可扩展到 API 调用级）。

### 5.5 专科病历模板、评估模板与护理联动

- 专科病历模板管理（6 级条款）+ 结构化数据元（诊断/分期/评估结果回写病历），引擎提供模板所需的结构化字段契约。
- 评估模板自动推荐：依据专科+诊断+当前 phase 推荐量表（如房颤→CHA₂DS₂-VASc），与医嘱推荐同一事件机制。
- 高风险护理评估结果主动通知医生：护理系统评估完成 → 引擎计分 → 达阈值发通知事件；中医病房可依据四诊/病因病位辨证内容（TCM 域的 observation 条件类型直接支持）。

## 6. 三个专科的复制策略

### 6.1 选科标准（评审原文即"重点优先"）

按四个维度打分：①是否国家/省级重点专科（评审明示优先）；②指南质量与稳定性（有权威专病指南或专家共识，更新节奏可控）；③医嘱结构化程度（套餐可枚举、变异相对少）；④本院数据基础（病历/医嘱/检验结构化完备、专家愿意深度参与审核）。

### 6.2 建议组合与理由

| 专科 | 角色 | 理由 |
|------|------|------|
| 心血管内科 | 锚定专科 | 已有 STEMI/暴发性心肌炎/肥厚型心肌病图谱资产；急危重症路径清晰、套餐化程度高、演示冲击力强（D2D 计时+再灌注套餐） |
| 血液科/肿瘤科 | 第二专科 | 已有淋巴瘤分期分型抽取资产（stage/histology/molecular_test 实体已在）；全周期长（化疗周期+随访），最能证明"全诊疗周期"覆盖 |
| 中医科 | 第三专科 | TCM 域辨证→治法→方药→禁忌流水线已成型；直接命中 32 项中医中药新增条款（十八反十九畏、中医临床路径、四诊结构化），一份投入双重得分 |

### 6.3 复制的是生产线，不是手工作坊

新增一个专科的标准化动作（目标：每专科 8–10 周，其中医学专员+专家投入约占总工时 60%）：

1. 指南遴选与版本登记（专科专家委员会确认）
2. 抽取模板配置（新专科 Profile 或复用 western + 模板）
3. 自动抽取 → 术语对齐 → 候选规则/套餐生成
4. 专家审核（走既有 review 门禁，审核记录即取证材料）
5. 医嘱套餐与院内字典映射（信息科+临床药事）
6. 路径建模与量表配置
7. 预检 → 灰度病区 → 全院发布
8. 演示脚本与制度文档同步归档

`domains/registry.py` 目前用心内科/血液科别名映射到 western——建议把 **specialty 升为 DomainProfile 的一等维度**（domain=specialty 二级结构），每专科独立知识包目录与 Profile 实例，避免三专科知识互相污染，也让"独立专科诊疗体系"在系统结构上可见（条款①）。

## 7. 组织与知识治理（⑤层）

评审不仅看系统，还看机制。建议落到纸面的制度与组织：

- **三方团队**：医学知识专员（2–3 人，编制知识资产）× 专科专家组（每专科 2–3 名，审核签字）× 信息科（集成、字典、发布运维）；质控科牵头指标。
- **制度文件清单**（评审材料）：专科知识库管理制度、知识审核与发布 SOP（对应已有 review 工作流的线上流程）、指南更新与知识包版本管理规程、应急停用预案（知识错误快速下线）、推荐采纳率与误报率监测例会。
- **审核即取证**：现有 review 队列/门禁/审计记录直接导出为评审证据——"每条知识谁审的、何时发布、依据哪版指南"可当场出示。
- **运营指标**：推荐触发量、卡片展示量、采纳率（分专科/分套餐）、核查拦截量、高危通知响应时长。采纳率是评审与院领导都关心的北极星，建议按月出报告。

## 8. 评审取证与演示设计

对四个能力域各设计一个端到端演示脚本（以心血管为例，其余专科同构复制）：

1. **专科独立性**：切换专科视图（Profile 驱动），分别展示心内/血液/中医三个知识包的图谱、规则数、指南清单与版本。
2. **全诊疗周期**：以一例胸痛患者从急诊到随访 6 个月的脱敏病例走全流程——入径→评估套餐→确诊（诊断规则证据链）→再灌注套餐（一键引用，剂量已按体重参数化）→监护与二级预防→出院评估→随访计划，HIS 侧展示医嘱闭环全状态。
3. **知识库溯源**：现场任选一条推荐医嘱，点开证据链翻到指南原文页码与引用句；打开审核记录展示两级审核签字；展示知识包版本历史与最近一次指南更新引发的 diff。
4. **医嘱推荐运行数据**：推荐量/采纳率报表（分专科、分月），核查拦截统计，高危通知响应记录；演示中医病房的四诊辨证内容驱动的推荐（加分项）。

数据准备：评审前 3–6 个月的真实运行数据积累（这也是为何路线图把试点上线排在评审前至少两个季度）。

| 指南更新滞后 | 版本化知识包 + 盯更 SOP；评审前梳理各专科指南"最新版本对照表" |
| 标准正式文本与征求意见稿差异 | 正式印发后跑一遍条款对照 diff，指标矩阵按正式文本重建 |
| 三个专科知识互相污染 | specialty 一等维度 + 独立知识包目录 + 包级预检 |
