## 一、建设背景与总体理解

电子病历评级中关于“具有独立专科诊疗体系、覆盖专科全诊疗周期的完整医嘱管理体系、符合专科指南要求的独立处理过程及专科知识库，并支持基于专病指南或专家共识的专科诊疗内容医嘱推荐”的要求，不应简单理解为建设一个 CDSS 提醒系统。

其本质是要求医院建立一套以**专科、专病为核心，以患者全诊疗周期为主线，以专科诊疗规范为依据，以医嘱为执行载体，以知识库和智能引擎为支撑**的专科诊疗信息化体系。

建议项目定位为**“医院专科专病诊疗一体化平台”**，CDSS 作为其中的智能决策子系统。平台应覆盖专科业务流程、专科数据管理、专科医嘱管理、专科知识管理、智能决策和专科质量管理，并与现有 HIS、EMR、LIS、PACS、护理系统、RDR 及 AI 平台协同建设。

### 1.1 评级要求拆解

| 评级要求 | 实际能力要求 | 对应建设内容 |
|---|---|---|
| 具有独立专科诊疗体系 | 专科具备独立诊疗规范、业务流程和管理机制 | 专科诊疗业务模型、专病管理、专科工作站 |
| 覆盖专科全诊疗周期 | 覆盖初诊、诊断、治疗、监测、出院、康复和随访 | 专科全病程管理、诊疗路径、随访管理 |
| 完整医嘱管理体系 | 专科医嘱有字典、组合、开立、执行、结果回传和追踪 | 专科医嘱中心、医嘱套餐、医嘱闭环 |
| 独立处理过程及专科知识库 | 诊疗过程有指南依据、知识支持和可执行规则 | 指南知识库、专病规则库、诊疗路径 |
| 专科诊疗内容医嘱推荐 | 结合患者状态、指南和禁忌证推荐医嘱 | 临床状态识别、规则推理、医嘱推荐引擎 |

**关键判断：**评级关注的不只是“有没有系统功能”，还包括这些功能是否融入真实临床流程、是否形成可追溯的患者诊疗记录、医嘱执行记录和医生决策记录。

## 二、总体建设目标与原则

### 2.1 总体目标

建设统一的专科专病诊疗一体化平台，形成以患者为中心、以专科为组织单元、以专病为管理对象、以诊疗路径为业务主线、以医嘱为执行载体、以知识库和规则引擎为智能支撑、以数据治理和质量管理为保障的专科诊疗体系。

### 2.2 建设原则

- **业务牵引、评级对标：**从重点专科真实诊疗流程出发，避免单纯堆砌知识库、规则和 AI 功能。
- **统一底座、专科配置：**公共数据、知识、规则、医嘱和流程能力统一建设，专科差异通过配置和扩展实现。
- **融入现有系统：**尽量嵌入医生工作站和现有临床系统，避免形成新的信息孤岛和重复录入。
- **确定性优先、安全可控：**临床高风险判断以经过审核的规则和算法为主，大模型用于辅助理解、抽取和解释。
- **全程闭环、可追溯：**覆盖推荐、确认、开立、执行、结果回传、后续处理及质量评价。
- **持续运营、动态更新：**建立指南、知识、规则、路径和医嘱套餐的版本管理及审核发布机制。

## 三、总体能力架构：六大体系

| 能力体系 | 核心定位 | 主要建设内容 |
|---|---|---|
| 专科诊疗业务体系 | 建立独立专科诊疗流程 | 专科门诊、住院、专病管理、MDT、康复、随访、诊疗路径 |
| 专科数据管理体系 | 提供准确、完整、及时的临床数据 | 专科数据集、专病档案、患者画像、数据标准化、实时数据服务 |
| 专科医嘱管理体系 | 实现专科医嘱标准化及闭环管理 | 医嘱字典、医嘱套餐、医嘱组合、开立与执行跟踪 |
| 专科知识管理体系 | 把指南和专家共识转化为可管理知识 | 指南库、疾病知识、评估知识、诊疗规则、医嘱知识 |
| 专科智能决策体系 | 基于患者状态提供可解释决策支持 | 状态识别、规则引擎、推理引擎、RAG、医嘱推荐 |
| 专科质量管理体系 | 评价诊疗规范执行及临床效果 | 路径质控、医嘱质控、病历质控、专科指标和持续改进 |

## 四、专科诊疗业务体系建设

### 4.1 建立“专科—专病—诊疗阶段”三级模型

建议以“专科”为组织单元，以“专病”为核心管理对象，以“诊疗阶段”为流程组织方式。例如心血管内科下设慢性心力衰竭、冠心病、心房颤动等专病；每个专病再按筛查初诊、诊断、病情评估、治疗、治疗监测、出院管理、康复和随访等阶段组织业务。

| 诊疗阶段 | 典型业务活动 |
|---|---|
| 筛查及初诊 | 主诉和病史采集、症状识别、必要检查 |
| 诊断 | 诊断标准判断、鉴别诊断、疾病分型 |
| 病情评估 | 评分量表、严重程度评估、风险分层 |
| 治疗 | 药物、手术、介入、器械及其他治疗 |
| 治疗监测 | 疗效评价、不良反应监测、指标趋势分析 |
| 出院管理 | 出院评估、出院医嘱、用药指导、复查计划 |
| 康复及随访 | 康复计划、定期复查、长期病情管理 |

### 4.2 建立标准化与个体化诊疗路径

标准化路径来源于国家临床路径、专病指南和行业规范；个体化路径根据患者合并症、禁忌证、病情变化和医生判断进行调整。

路径应支持：

- 节点配置；
- 执行状态跟踪；
- 路径变异记录；
- 变异原因记录；
- 路径版本管理；
- 完成率统计。

不建议将临床路径设计为固定医嘱套餐。临床路径应是可根据患者状态动态调整的诊疗过程模型，医嘱套餐只是其中可复用的执行组件。

## 五、专科数据管理体系建设

### 5.1 建立专科标准数据集

建议由 RDR 承担数据治理、标准化和专病数据集建设能力，并通过临床实时数据服务为诊疗决策提供当前数据。专科数据集应覆盖基础信息、病史、症状体征、检验、检查、诊断、用药、治疗、护理和随访等数据。

| 数据类别 | 示例数据 | 主要来源 |
|---|---|---|
| 基础信息 | 年龄、性别、身高、体重 | HIS/EMR |
| 病史信息 | 既往史、合并症、过敏史 | EMR |
| 症状体征 | 呼吸困难、水肿、血压、心率 | EMR/护理 |
| 检验数据 | BNP、NT-proBNP、肌酐、电解质 | LIS |
| 检查数据 | 心脏超声、心电图、影像结果 | PACS/检查系统 |
| 诊断数据 | 疾病诊断、分型、分期 | HIS/EMR |
| 用药及治疗 | 药品、剂量、频次、手术和介入记录 | HIS/EMR |
| 随访数据 | 症状变化、复查结果、再入院情况 | 随访系统/EMR |

### 5.2 建立统一数据标准和映射

- 统一专科数据元、术语、编码、单位、值域和数据类型。
- 建立 HIS、LIS、PACS、EMR 原始项目与标准数据元之间的映射关系。
- 保留原始值、标准化值、来源系统、采集时间和转换规则，确保可追溯。
- 对关键临床数据设置完整性、及时性、准确性和一致性校验。

### 5.3 区分临床实时数据与科研历史数据

RDR 适合承担历史数据治理、专病数据集、科研分析和质量评价；临床实时决策则应通过稳定的数据接口或临床数据服务获取当前诊疗数据。不能简单依赖科研数据仓库承担全部实时决策职责。

### 5.4 建立专病患者档案

同一患者可同时纳入多个专病管理体系，例如慢性心衰、冠心病和糖尿病。应统一患者主索引和原始诊疗数据，专病档案分别维护诊断、评估、风险分层、治疗、医嘱、关键指标和随访记录，避免重复建档和数据冲突。

## 六、专科医嘱管理体系建设

### 6.1 建立专科医嘱字典

在全院 HIS 医嘱字典基础上，建立专科医嘱分类、适用疾病、适用阶段、适用条件、执行要求和知识依据等专科属性。专科医嘱字典应引用全院标准药品、检查、检验和治疗项目，不宜另建一套与 HIS 脱节的医嘱主数据。

| 医嘱类别 | 典型内容 | 管理重点 |
|---|---|---|
| 检验医嘱 | BNP、肌钙蛋白、电解质、肾功能 | 适用阶段、频次、结果回传 |
| 检查医嘱 | 心脏超声、心电图、动态心电图 | 检查目的、适应证、重复检查控制 |
| 药物医嘱 | 指南推荐药物及治疗组合 | 适应证、禁忌证、剂量、相互作用 |
| 治疗医嘱 | 氧疗、心脏康复、液体管理 | 执行条件、疗程、效果监测 |
| 护理医嘱 | 生命体征监测、出入量管理 | 频率、执行责任、异常处理 |
| 随访医嘱 | 出院复查、电话或线上随访 | 时间节点、任务提醒、结果记录 |

### 6.2 建立专科医嘱套餐

可按诊疗阶段和临床场景配置套餐，例如心衰初诊评估套餐、药物治疗监测套餐、出院管理套餐。套餐应支持：

- 专科配置；
- 项目组合；
- 适用条件；
- 版本管理；
- 一键引用；
- 执行跟踪。

套餐项目必须经过患者状态过滤，不能替代医生个体化判断。

### 6.3 建立医嘱全流程闭环

建议形成：

**医嘱推荐 → 医生确认 → 医嘱开立 → 护士接收 → 医嘱执行 → 结果回传 → 结果分析 → 后续诊疗调整。**

医嘱与诊疗路径节点建立关联，系统不仅记录医嘱是否开立，还应记录是否执行、结果是否回传以及是否完成后续处理。

## 七、专科知识管理体系建设

### 7.1 建立分层专科知识库

| 知识类别 | 主要内容 | 主要用途 |
|---|---|---|
| 指南知识库 | 国家指南、国际指南、专家共识及其版本 | 提供诊疗依据 |
| 疾病知识库 | 疾病定义、分型、诊断标准、分期 | 疾病识别和分类 |
| 评估知识库 | 评分量表、风险分层、计算公式 | 患者评估 |
| 诊疗规则库 | 诊断、治疗、适应证、禁忌证、监测规则 | 临床决策 |
| 医嘱知识库 | 检查、检验、药物、治疗和随访建议 | 医嘱推荐 |

### 7.2 将指南内容结构化

以慢性心衰指南为例，应提取诊断标准、NYHA 分级、LVEF 分型、相关检验指标、药物治疗适应证、禁忌证、剂量调整原则、随访要求和并发症处理要求。

PDF 文档和 RAG 检索可作为知识获取入口，但临床执行所需的关键知识必须经过结构化、审核和版本管理。

### 7.3 建立专科知识图谱

知识图谱可组织疾病、症状、体征、检查、检验指标、药品、治疗方案、并发症、风险因素和指南推荐等实体及其关系。例如：

- 慢性心衰 — 需要评估 — LVEF；
- 某种疾病 — 需要检测 — 特定检验指标；
- 某药物 — 存在禁忌证 — 特定临床状态；
- 指南推荐 — 对应 — 特定治疗方案。

知识图谱用于知识关联和语义组织，但不能代替规则引擎完成临床推理。

### 7.4 建立知识全生命周期管理

- 每条知识记录来源、指南名称及版本、发布机构、发布时间、适用疾病、人群和场景。
- 建立专业审核、临床验证、发布、生效、更新、停用和追溯机制。
- 规则和医嘱推荐应关联具体知识依据，支持查看来源和版本。
- 建立知识更新责任人和周期，及时评估指南更新对规则、路径和医嘱套餐的影响。

## 八、专科智能决策体系建设

### 8.1 临床状态识别引擎

将原始临床数据转换为可供规则调用的结构化临床状态。例如心衰患者的 LVEF 分型、血压状态、心率状态、肾功能状态、血钾状态、当前治疗状态等。

优先使用结构化数据和确定性计算；NLP 及大模型用于病历文本抽取、信息补全和辅助解释。

### 8.2 专科决策规则引擎

| 规则类型 | 功能 | 示例 |
|---|---|---|
| 诊断规则 | 判断疾病或分型条件 | 心衰诊断辅助、LVEF 分型 |
| 评估规则 | 计算严重程度和风险 | NYHA、风险评分 |
| 治疗规则 | 判断治疗适应证和禁忌证 | 药物适用条件、禁忌证判断 |
| 医嘱规则 | 推荐检查、检验、药物和随访医嘱 | 专科检查套餐、监测建议 |

建议采用**规则引擎 + 工作流引擎 + 知识图谱 + AI 辅助理解**的组合：

- 规则引擎承担确定性判断；
- 工作流引擎管理诊疗阶段和任务流转；
- 知识图谱组织知识关系；
- RAG 提供指南依据检索；
- 大模型辅助病历理解、信息抽取和解释。

### 8.3 专科医嘱推荐引擎

推荐流程：

```text
患者进入专科诊疗
        ↓
获取患者数据
        ↓
识别临床状态
        ↓
匹配专病和诊疗阶段
        ↓
查询指南及知识库
        ↓
调用规则引擎
        ↓
判断适应证和禁忌证
        ↓
生成诊疗建议及医嘱组合
        ↓
医生确认、修改或拒绝
        ↓
HIS/EMR正式开立
        ↓
执行及结果回传
```

每条推荐应展示：

1. 推荐内容；
2. 推荐原因；
3. 患者相关指标；
4. 指南依据；
5. 适用条件；
6. 禁忌证和注意事项。

同时记录医生采纳、修改或拒绝及原因。正式医嘱应由医生确认后进入 HIS 医嘱流程。

### 8.4 技术职责边界

| 技术组件 | 核心职责 | 建议边界 |
|---|---|---|
| 规则引擎 | 确定性条件判断、适应证和禁忌证检查 | 规则可测试、可审计、可版本化 |
| 知识图谱 | 疾病、指标、药物及治疗知识关联 | 不单独承担临床决策 |
| 工作流引擎 | 诊疗路径、任务和状态流转 | 不替代临床规则判断 |
| RAG | 指南、共识和知识依据检索 | 检索结果不能直接等同于医嘱 |
| 大模型 | 病历理解、文本抽取、解释和辅助分析 | 不直接决定或执行高风险医嘱 |
| 推荐服务 | 整合患者状态、规则和医嘱字典 | 输出结构化、可解释的推荐结果 |

## 九、专科质量管理体系建设

### 9.1 诊疗路径质控

- 必要检查是否完成；
- 专病评估是否完成；
- 治疗是否符合指南要求；
- 路径变异是否记录及说明原因；
- 出院评估和随访计划是否完成。

### 9.2 医嘱及病历质控

- 医嘱是否符合疾病适应证和禁忌证要求；
- 药物剂量、频次及疗程是否合理；
- 是否存在不合理重复检查；
- 医嘱执行及结果回传是否闭环；
- 专科病历是否记录关键指标、评分和诊疗依据。

### 9.3 专科质量指标

| 指标类别 | 建议指标 |
|---|---|
| 专科覆盖 | 专科患者纳入率、专病路径覆盖率 |
| 诊疗规范 | 专病评估完成率、关键检查完成率、指南推荐治疗符合率 |
| 医嘱闭环 | 专科医嘱使用率、医嘱执行闭环率、结果回传率 |
| 智能推荐 | 推荐触达率、采纳率、修改率、拒绝原因分布 |
| 数据质量 | 关键数据完整率、准确率、及时率 |
| 长期管理 | 出院随访完成率、复查完成率、再入院等临床结果指标 |

质量指标应结合专科特点、医院管理要求和正式评价口径确定。不能仅以医生是否点击推荐作为应用成效，应关注推荐是否合理、医嘱是否执行以及诊疗过程是否完整。

## 十、与现有系统的关系及总体技术架构

### 10.1 系统职责边界

| 系统/平台 | 核心职责 | 在整体体系中的定位 |
|---|---|---|
| HIS | 医嘱、药品、检查检验申请及执行业务 | 正式医嘱及业务执行入口 |
| EMR | 病历书写、诊疗记录 | 临床诊疗记录入口 |
| LIS/PACS/护理等 | 检查检验、影像、护理执行 | 临床数据及执行结果来源 |
| RDR | 数据治理、标准化、专病数据集、科研分析 | 专科数据底座 |
| CDSS | 规则提醒、临床决策支持 | 智能决策应用能力 |
| AI 平台 | 大模型、NLP、RAG、智能体及模型管理 | AI 技术支撑 |
| 专科诊疗平台 | 专科路径、专病管理、专科医嘱、知识管理和质控 | 统一专科业务主体 |

### 10.2 五层技术架构

| 架构层 | 核心模块 | 主要职责 |
|---|---|---|
| 临床业务接入层 | HIS、EMR、LIS、PACS、护理、手术麻醉 | 现有业务系统接入 |
| 专科数据服务层 | 专科数据集、患者画像、专病档案、标准化服务 | 提供统一患者数据 |
| 专科知识中心 | 指南库、知识图谱、医嘱库、规则库、路径库 | 管理专科诊疗知识 |
| 智能决策引擎层 | 状态识别、规则引擎、推理、RAG、AI 模型、推荐服务 | 提供诊疗决策支持 |
| 专科应用层 | 专科工作站、医嘱推荐、专病管理、质控管理 | 面向医生和管理人员 |

横向公共能力包括统一身份认证、权限管理、数据安全、日志审计、知识审核、版本管理、接口管理和运行监控。

### 10.3 技术选型建议

| 能力领域 | 可选技术方向 | 选型建议 |
|---|---|---|
| 系统集成 | ESB、HIP、API Gateway、消息中间件 | 优先复用医院既有集成平台 |
| 数据治理 | RDR、数据中台、标准术语服务 | 复用现有 RDR 能力 |
| 结构化知识存储 | 关系型数据库、图数据库 | 关系型数据库管理业务数据，图数据库按需承载知识关系 |
| 指南文档检索 | RAGFlow 或自研 RAG | 用于文档解析、检索和依据呈现 |
| 规则引擎 | Drools 或轻量自研规则服务 | 结合规则复杂度、团队能力和维护成本选择 |
| 工作流 | Flowable 等 | 用于路径、任务和审批流转 |
| AI 应用编排 | Dify、LangGraph 或自研服务 | 用于模型调用、NLP 和复杂 AI 流程 |
| 推荐服务 | 自研业务编排服务 | 负责患者状态、规则、医嘱字典整合 |

不建议将所有功能集中在 Dify 或 LangGraph 中。临床规则判断、医嘱管理、医嘱执行和路径管理应建设为独立、可测试、可审计的业务服务。

## 十一、分阶段实施路径

| 阶段 | 重点建设内容 | 阶段成果 |
|---|---|---|
| 第一期：专科业务标准化 | 选择试点专科；梳理专病、诊疗阶段、路径、数据集和医嘱字典 | 形成专科诊疗基础体系 |
| 第二期：专科知识体系建设 | 指南知识库、知识图谱、规则库、专病评估模型和医嘱套餐 | 形成结构化、可维护的专科知识体系 |
| 第三期：智能决策建设 | 临床状态识别、规则引擎、推理服务、医嘱推荐和路径智能管理 | 形成专科智能决策能力 |
| 第四期：全程闭环和质量运营 | 医嘱执行闭环、结果回传、随访管理、专科质控和效果评价 | 形成全诊疗周期闭环及持续改进机制 |

建议先选择 2—3 个重点专科试点，优先选择业务基础较好、专病指南明确、诊疗路径相对成熟、临床团队参与度高的专科。试点成功后沉淀可复用的数据模型、知识模型、规则模型和医嘱模型，再向其他专科推广。

## 十二、项目验收与评级证据准备

| 评价关注点 | 系统功能证据 | 临床应用证据 |
|---|---|---|
| 独立专科诊疗体系 | 专科工作站、专病管理、专科路径配置 | 专科实际使用记录和业务流程记录 |

验收应同时检查功能、数据、流程和真实应用情况。具体评级条款、分级要求和证据口径应以项目申报时适用的国家及地方正式文件、评价细则和现场评审要求为准。

## 十三、重点建设建议与风险控制

### 13.1 项目定位不宜局限于 CDSS

建议项目命名为**“医院专科专病诊疗一体化平台建设项目”**。CDSS 是智能决策子系统，不能覆盖专科业务流程、医嘱管理、知识管理、全病程和质量管理的全部要求。

### 13.2 以医嘱为核心连接诊疗与执行

专科医嘱应成为体系中的核心业务对象。将医嘱推荐嵌入医生工作站，支持转换为可编辑的正式医嘱，并追踪开立、执行、结果回传和后续处理。

### 13.3 建设统一知识中心

采用“公共医学知识层 + 专科知识层 + 专病规则层”的组织方式。公共知识和平台能力统一维护，专科维护专业知识、路径和规则，专病层承载更细粒度的适用条件和处理逻辑。

### 13.4 确定性规则与 AI 协同

病历抽取、指南解析和解释可使用大模型；评分计算、适应证、禁忌证和关键医嘱规则应采用确定性算法或规则引擎。高风险建议必须保留医生审核确认，并记录模型、规则、知识版本和决策过程。

### 13.5 打通临床与科研数据闭环

形成：

**临床诊疗 → 专病数据采集 → 数据治理 → 质量分析 → 临床科研 → 知识和规则优化 → 反哺临床。**

临床数据回流科研平台时应做好授权、脱敏、权限控制和用途管理。

## 十四、推荐的项目交付清单

1. 专科诊疗业务模型及专病目录。
2. 专科诊疗路径及路径版本管理。
3. 专科标准数据集、数据元和编码映射。
4. 专病患者档案及患者临床状态模型。
5. 专科医嘱字典、医嘱套餐和医嘱映射关系。
6. 指南、共识及结构化专科知识库。
7. 专科知识图谱及知识版本管理机制。
8. 专科诊疗规则库、规则引擎和推理服务。
9. 专科医嘱推荐服务及医生交互记录。
10. 医嘱开立、执行、结果回传和后续处理闭环。
11. 专科质控指标、质量看板和持续改进机制。
12. 系统接口规范、权限安全、日志审计和运维监控。
13. 试点专科临床应用报告及评级证据材料。

## 十五、总结

建议以**专科诊疗平台作为业务主体**，以**知识中心和决策引擎作为公共能力**，以 **RDR 和 AI 平台作为底层支撑**，复用 HIS、EMR 及医院集成平台完成医嘱和临床业务闭环。

最终形成：

> 以患者为中心、以专科为组织单元、以专病为管理对象、以诊疗路径为业务主线、以医嘱为执行载体、以知识库和规则引擎为智能支撑、以数据治理和质量管理为保障。

该体系既可响应电子病历评级相关要求，也可支撑重点专科建设、专病中心建设和临床科研。
